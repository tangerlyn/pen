## 1. 문제 정의

리뷰는 PENGWYN의 핵심 콘텐츠다. "리뷰 작성 화면에 들어온 사람 중 몇 %가 등록까지 가는가, 어디서 그만두는가"를 알고 싶었다.

다만 출시 전이라 사용자가 없다. 그래서 목표를 분석이 아니라 **나중에 나올 숫자를 믿을 수 있게 만드는 것**으로 잡았다. 로그가 틀리면 그 위에서 나온 전환율도 틀리기 때문이다.

사용자 데이터가 없는 대신 대조할 정답이 두 개 있었다.
- **서버의 정답**: Firestore `reviews` 컬렉션. 리뷰가 실제로 저장됐는지, 사진이 몇 장인지
- **행동의 정답**: 내가 직접 수행한 QA 시나리오 기록. 어디서 들어가서 무엇을 했는지

로그를 이 둘과 맞춰 보는 구조를 만드는 것이 이 프로젝트의 중심이다.

## 2. 설계 결정

| 결정 | 이유 |
|---|---|
| 작성 시도마다 `write_session_id`(UUID) 발급 | GA4 기본 세션은 앱 세션 단위라 한 번 켠 앱에서 리뷰를 두 번 쓰면 구분이 안 된다. 이 ID가 없으면 "등록은 됐는데 작성 시작 기록이 없는 경우" 같은 검증 쿼리를 짤 수 없다 |
| 저장 버튼 탭(`attempt`)과 저장 성공(`success`)을 분리 | 버튼을 눌렀다고 저장된 게 아니다. 성공은 Firestore 쓰기가 끝난 순간에만 남긴다. 실패는 이미지 업로드·인증·DB 쓰기 중 어디서 났는지 구분한다 |
| "작성 시작" = 첫 사용자 입력 | 화면 진입과 작성 시작을 구분해야 "들어왔다가 아무것도 안 하고 나간" 비율을 볼 수 있다. 제품 상세에서 들어올 때의 자동 태깅은 사용자 입력이 아니므로 제외 |
| 퍼널 = 세션 안에서 도달했는지 | 사진을 제목보다 먼저 넣을 수 있다. 순서로 정의하면 정상 행동이 이탈로 잡힌다 |
| 성공 로그에 `review_id` 포함 | Firestore 문서와 1:1로 조인하는 키. 이게 있어야 로그 유실과 유령 성공을 잡을 수 있다 |
| 진입 경로 `entry` 파라미터 + `unknown` 감지 | 홈과 리뷰 피드가 같은 경로로 이동해서 구분이 안 됐다. 명세에 없는 진입점이 생기면 `unknown`으로 남겨 검증 규칙이 잡게 했다 |
| 글 내용은 수집하지 않음 | 제목·본문은 길이만 남긴다. 분석에 필요한 최소한만 |
| 사용자 행동은 Analytics, 운영 오류는 Crashlytics | EXP 지급 실패는 사용자가 한 행동이 아니므로 퍼널 로그를 오염시키지 않게 분리 |

## 3. 로그를 설계하다가 찾은 데이터 정합성 문제

로그를 어디에 심을지 정하려고 저장 흐름을 따라가다가, 같은 리뷰가 두 번 저장될 수 있는 경로를 세 개 찾았다.

| 문제 | 원인 | 조치 |
|---|---|---|
| 리뷰는 저장됐는데 에러가 뜸 → 다시 누르면 중복 리뷰 | 리뷰 저장 후 EXP 지급이 같은 `try` 안에 있어서, EXP 지급만 실패해도 전체가 실패로 처리됨 | EXP 실패는 Crashlytics에만 기록하고 등록은 성공 처리 |
| 업로드 중 완료 버튼 연타 → 중복 리뷰 | 버튼 비활성화 기준(`isLoading`)이 이미지 업로드가 **끝난 뒤에야** 켜짐 | 버튼 탭부터 저장 완료까지 막는 가드 추가 |
| 저장은 됐는데 응답만 실패한 경우 재시도 → 중복 리뷰 | 저장할 때마다 새 문서 ID 생성 | 문서 ID를 화면 진입 시 한 번만 정함. 다시 저장해도 같은 문서를 덮어씀(멱등) |

세 번째 조치 덕분에 로그의 `review_id`와 Firestore 문서 ID가 항상 같은 값이 됐다. 데이터 정합성 수정이 그대로 검증 설계의 조인 키가 됐다.

## 4. 검증

### 4-1. 앱: 이벤트 순서 단위 테스트

로거를 인터페이스로 감싸고 테스트에서는 기록만 하는 가짜 로거를 끼웠다. 명세의 시나리오대로 동작시키고 이벤트 순서와 파라미터를 확인한다. 11개, 전부 통과.
- 예: 사진 없이 등록 → 막힘 → 사진 추가 후 재시도하면 `attempt_no`가 1, 2로 이어지는가
- 예: 등록 성공 뒤에는 어떤 이벤트도 남지 않는가 (성공과 이탈이 한 세션에 같이 찍히면 안 됨)

### 4-2. 실기기 1차 대조 (2026-10-12, iOS TestFlight)

리뷰 2건을 작성하고 Analytics 실시간 보고서의 `review_submit_success` 2건과 Firestore 문서를 대조했다. **`review_id` 2개가 Firestore 문서 ID와 1:1로 일치**했고, 중복 문서는 없었다.

### 4-3. BigQuery 검증 규칙 14개

GA4 원본은 이벤트 파라미터가 중첩 배열이라 매번 풀어 써야 한다. 그래서 정제 뷰(`stg_review_events`)에서 한 번만 펼치고, 세션 단위 마트를 거쳐 규칙을 적용했다. 원천 스키마를 아는 곳이 한 군데뿐이라 파라미터가 바뀌어도 한 파일만 고치면 된다.

| 품질 차원 | 규칙 |
|---|---|
| 완전성 | 성공했는데 진입·시작 기록이 없음, 시도 뒤에 결과가 없음 |
| 유일성 | 진입 중복, 같은 리뷰의 성공 중복 |
| 일관성 | 성공과 이탈이 공존, 이벤트 순서 역전 |
| 정확성 | 로그의 사진 수 vs Firestore, 시도 vs 성공, 추가·삭제 합계 vs 시도 |
| 유효성 | 필수 값 누락, 명세에 없는 값 |
| 정합성 | Firestore에는 있는데 로그 없음(유실), 로그는 있는데 Firestore에 없음(유령 성공) |
| 적시성 | 24시간 넘게 늦게 수집된 이벤트 |

**오탐을 줄이려고 한 판단**
- **삭제된 리뷰**: Firestore 확장의 최신 상태 뷰는 삭제된 문서를 뺀다. 그대로 쓰면 "썼다가 지운 리뷰"가 유령 성공으로 잡힌다. 변경 이력 테이블에서 "존재한 적이 있는지"로 판단했다.
- **수정된 리뷰**: 사진 수는 최신 문서가 아니라 생성 시점 스냅샷과 비교한다. 수정 모드의 성공 로그는 같은 `review_id`로 정상 발생하므로 중복 검사에서 뺐다.
- **아직 도착 안 한 데이터**: Firestore는 실시간, GA4는 다음 날 도착한다. 유실 검사는 GA4 테이블이 도착한 날짜까지만 본다.
- **늦게 오는 이벤트**: GA4는 늦게 올라온 이벤트를 원래 날짜에 나중에 반영한다. 일일 점검은 최근 7일을 지우고 다시 계산하므로 몇 번을 돌려도 결과가 같다.

### 4-4. 검증 쿼리를 검증하기

검증 쿼리가 틀리면 "문제없음"이라는 결과도 믿을 수 없다. GA4 export·Firestore 변경 이력과 같은 스키마로 가짜 데이터를 만들어 테스트 데이터 세트에 올렸다.
- **정상 시나리오** (S1~S4, S9, 업로드 실패 후 이탈, 작성 후 삭제, 디버그 빌드, 로깅 이전 문서 등) → 어떤 규칙에도 걸리면 안 됨
- **규칙마다 일부러 심은 위반 1건** → 그 규칙에만 정확히 1건 걸려야 함

14개 규칙 모두 오탐·미탐 0, 일일 점검 잡 재실행 결과 동일.

이 테스트에서 실제로 버그를 하나 잡았다. 한 세션이 이벤트 두 개에서 같은 잘못된 값을 남기면 위반이 2건으로 세졌다. **위반 건수 = 위반한 대상(세션·리뷰) 수**로 정의를 고쳤다.

실데이터를 넣고 나서 규칙 하나를 더 고쳤다. DQ-12(로그 유실)는 "확장 설치 뒤에 생성된 문서"만 검사하고 있었다. 그런데 확장은 로깅 배포보다 늦게 설치돼서, 그 사이에 쓴 리뷰는 백필(IMPORT)로만 들어온다. 실기기에서 직접 쓴 리뷰 2건이 바로 이 경우라 검사에서 빠지고 있었다. 확장 설치 시점은 로그 수집과 아무 관계가 없으므로 기준을 문서의 `createdAt` 하나로 바꾸고, 백필 문서의 유실을 심은 위반을 테스트에 추가했다.

첫 실데이터 점검 결과를 보다가 집계 구조의 결함도 하나 찾았다. 일일 점검은 "점검했고 문제없음"을 보여주려고 위반이 없는 규칙도 0건으로 남기는데, Firestore만 보는 DQ-12까지 앱 빌드 환경(`testflight`)별로 0을 채우고 있었다. DQ-12의 위반은 환경 구분 없이(`n/a`) 기록되므로 그 0은 검사 결과가 아니라 **원래 0일 수밖에 없는 값**이었다. 규칙마다 집계 범위(`env_scope`)를 두어 0은 실제로 검사한 범위에만 채우게 고치고, "검사하지 않는 범위에 0이 채워지지 않는지"를 테스트 항목으로 추가했다.

## 6. 한계와 다음 단계

- **표본이 작다.** 테스터 데이터라 퍼널 전환율은 해석하지 않는다. 이 프로젝트에서 검증한 건 숫자가 아니라 숫자를 만드는 구조다.
- **등록 시각이 기기 시계 기준이다.** Firestore `createdAt`도 기기 시각이라 서로는 맞지만 기기 시간이 틀리면 둘 다 틀린다. 서버 타임스탬프 필드를 따로 두는 것이 다음 개선이다.
- **로깅 이전 앱 버전을 구분할 수 없다.** Firestore 문서에 앱 버전이 없어서, 출시 후 구버전 사용자가 쓴 리뷰는 로그 유실(DQ-12)로 잡힌다. 리뷰 문서에 `appVersion`을 남기면 해결된다.
- **화면 조회 로그가 없다.** 현재 화면 이름이 전부 `FlutterViewController`로 수집된다. 라우터 화면 전환을 `screen_view`로 남기는 설계가 다음 과제다.
